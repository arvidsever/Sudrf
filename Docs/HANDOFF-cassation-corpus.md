# Хендофф: правовая база судебных актов КСОЮ

Документ для продолжения работы на машине с прямым доступом к `*.sudrf.ru` (из песочницы
Claude домен закрыт: `403 host_not_allowed`). Всё, что можно было сделать без сети и без
Swift-тулчейна, уже сделано; дальше нужен живой прогон.

**Требуется:** Mac с Xcode 26 (для `swift test`) и сеть без ограничений на `sudrf.ru`.

## Цель проекта

Собирать с сайтов девяти кассационных судов ОСЮ судебные акты и строить по ним правовую
базу с поиском: полнотекстовым, по реквизитам, по цитируемым нормам и семантическим.
Пилот — один КСОЮ, затем масштабирование.

**Целевая архитектура** (решения приняты, обсуждать заново не нужно):

- харвестер, база и API — на российском VPS, Python;
- Postgres 16 + `pgvector` + `pg_trgm`; полнотекст на `to_tsvector('russian')`;
- слой сырых HTML (`raw/<домен>/<год>/<id>.html.zst`) как источник истины — парсеры здесь
  заведомо будут дорабатываться, и архив избавляет от повторного обхода судов;
- капча — CNN из проекта `sudtudtestbot` (использование разрешено автором);
- `Sudrf` (это приложение) остаётся интерактивным инструментом юриста и позже может стать
  клиентом того же API. Сбор в него не встраивается.

## Задача 1. Живая разведка (блокирует всё остальное)

Шесть запросов закрывают то, что известно только из проекта двухлетней давности
(`sudrfscraper`). Порядок важен: пункт 1 либо подтверждает механику целиком, либо отменяет.

Удобно смотреть через `curl`, сайт в cp1251:

```bash
curl -s '<URL>' | iconv -f cp1251 -t utf-8 | grep -o 'Всего по запросу найдено[^<]*'
```

### 1.1. Перечень работает

`2kas.sudrf.ru` выбран потому, что капчи на поиске там нет — механика проверяется
без лишней переменной.

```
https://2kas.sudrf.ru/modules.php?name=sud_delo&srv_num=1&name_op=r&page=1&delo_id=2800001&case_type=0&new=2800001&delo_table=g33_case&g33_case__ENTRY_DATE1D=01.06.2026&g33_case__ENTRY_DATE2D=07.06.2026&Submit=%CD%E0%E9%F2%E8
```

Ожидание: таблица `<table id="tablcont">` со строками дел и счётчик «Всего по запросу
найдено — N» сверху.

Если пусто — попробовать полный набор пустых полей формы, как его шлёт `sudrfscraper`
(возможно, движок требует именно полную форму):

```
https://2kas.sudrf.ru/modules.php?name=sud_delo&srv_num=1&name_op=r&page=1&vnkod=&delo_id=2800001&case_type=0&new=2800001&G33_PARTS__NAMESS=&g33_case__CASE_NUMBERSS=&g33_case__JUDICIAL_UIDSS=&delo_table=g33_case&g33_case__ENTRY_DATE1D=01.06.2026&g33_case__ENTRY_DATE2D=07.06.2026&G33_CASE__COURT_I_REGION_ID=&G33_CASE__COURT_I=&G33_CASE__CASE_NUMBER_ISS=&g33_case__RESULT_DATE_I1D=&g33_case__RESULT_DATE_I2D=&G33_CASE__M_SUB_TYPE=&G33_CASE__WRIT_TYPE=&G33_CASE__JUDGE=&g33_case__RESULT_DATE1D=&g33_case__RESULT_DATE2D=&G33_CASE__RESULT=&G33_CASE__BUILDING_ID=&G33_CASE__COURT_STRUCT=&G33_CASE__JUDGE_I=&G33_EVENT__EVENT_NAME=&G33_EVENT__EVENT_DATEDD=&G33_PARTS__PARTS_TYPE=&G3_DOCUMENT__PUBL_DATE1D=&G3_DOCUMENT__PUBL_DATE2D=&Submit=%CD%E0%E9%F2%E8
```

### 1.2. Пагинация

Тот же URL с `&page=2`, `&page=3`. Ожидание: новые строки, а не повтор первой страницы.
Заодно посчитать, сколько строк на странице (у `sudrfscraper` в логах фигурирует 25).

### 1.3. Диапазоны дат

- сузить окно до одного дня — число дел должно упасть;
- проверить `g33_case__RESULT_DATE1D/2D` (дата рассмотрения);
- **отдельно и обязательно** — `G3_DOCUMENT__PUBL_DATE1D/2D` (дата публикации акта).
  От него зависит вся схема инкрементального добега: акт часто публикуется много позже
  рассмотрения, и без этого фильтра придётся каждый раз перечитывать всё окно.
  Обратите внимание на префикс: у документа он короче (`G3_`), чем у дела (`G33_`).

### 1.4. Ссылка на текст акта

В строке выдачи посмотреть **последнюю колонку**: есть ли там `<a>` на текст акта.
Если есть — открыть и сверить с текстом из вкладки «Судебные акты» карточки
(`name_op=case`, блоки `cont_doc{N}`).

Это вопрос экономики сбора: строка выдачи уже несёт номер, дату поступления, стороны,
судью, дату решения и результат. При живой ссылке на текст **хватает одного запроса
на дело** вместо двух, то есть корпус собирается вдвое быстрее.

### 1.5. `srv_num` — главный риск полноты

Тот же URL с `srv_num=2`, затем `srv_num=3`. Вопросы:

- отдают ли данные вообще;
- различаются ли выборки, или это зеркала;
- совпадает ли сумма по всем экземплярам со счётчиком «Всего найдено».

Если дела распределены между экземплярами, обход только первого даёт **молча неполный
корпус** — суд отвечает валидной страницей, просто без части строк. Это худший из рисков
проекта, потому что не проявляется как ошибка.

### 1.6. `delo_id` кассационных картотек

Подтвердить нормализованные значения и решить спор по КАС-кассации — источники расходятся:

```
КАС, вариант А:  &delo_id=43&case_type=0&new=0&delo_table=p33_case
КАС, вариант Б:  &delo_id=2550001&case_type=0&new=0&delo_table=adm33_case
```

Вариант Б — из `sudtudtestbot` со ссылкой на живую проверку дела 16-2843/2026; вариант А —
из `sudrfscraper`, навыка и нашего кода. Уголовная кассация для сверки:
`&delo_id=2450001&new=2450001&delo_table=u33_case`.

### 1.7. Капча на перечне

На `3kas.sudrf.ru` (капча есть) тот же прогон. Проверить связку: модель решила →
пара `captcha`+`captchaid` действует на весь регион → перечень идёт без новых капч.
Померить, сколько страниц проходит на одной паре.

**Каждый ответ сохранить фикстурой** — по инварианту репозитория новый вариант страницы
сопровождается парсером и фикстурным тестом.

## Задача 2. Правки в `SudrfKit` по итогам разведки

1. **`delo_id` кассации.** `CartotekaRegistry.cassationSOYu`
   (`Sources/SudrfKit/Cartoteka.swift:359-387`) хранит короткие `5` / `4` с длинным `new`,
   а три внешних источника для выдачи требуют нормализованные `2800001` / `2450001`.
   Правка отложена сознательно: для карточки и поиска по номеру текущие значения работают,
   и менять их вслепую — риск для работающего приложения. После пункта 1.6 поправить
   и закрыть тестом в `CartotekaRegistryTests`.
2. **Ротация `srv_num` в `SudrfClient`.** Параметр в URL-строителе уже есть, клиентского
   перебора нет намеренно — это изменение поведения приложения. Включать только после
   пункта 1.5, с тестом на то, что перебор останавливается на исчерпании.
3. **Ссылка на текст в `ResultsParser`.** `Sources/SudrfKit/ResultsParser.swift:17` цепляется
   только за `a[href*=name_op=case]`. Для приложения это неважно, для сбора существенно —
   добавить, если пункт 1.4 подтвердится.

## Задача 3. Капча под Linux

Цель — рабочая модель в Python. По убыванию предпочтительности:

1. **Взять у друга `server/captcha-model.json`.** В присланный архив он не попал
   (`.gitignore`), как и корпус `data/captcha-training/`. Это веса CNN на чистом JS,
   а архитектура описана рядом в `server/captcha.js`:
   `CNN = { IW: 64, IH: 20, C1: 8, C2: 16, K: 3, PAD: 1, HID: 64, HEADS: 5, NC: 10 }`,
   forward-проход там же. Пять слоёв читаются в NumPy напрямую — ONNX не нужен вообще.
   Даёт сразу проверенные 97,9 % по цифрам.
2. **Переобучить** ту же архитектуру в PyTorch на объединённом корпусе (у друга
   `data/captcha-training/solved/`, у нас
   `~/Library/Application Support/Sudrf/captcha-training/solved-numeric/`) и выгрузить
   в ONNX. Сетка крошечная, полчаса на CPU.
3. Конвертация CoreML → ONNX — **не надо**: `coremltools` односторонний, конвертер
   в `onnxmltools` заброшен. Оставлено как последний вариант.

Обязательно перенести поведенческие правила (детали — в `ksoyu-listing-grammar.md`, §5):
портал держит одну капчу на IP по несколько минут и не меняет её от неверных ответов;
решённая пара действует на весь регион около 6 часов; у антибрутфорс-судов (известен
Краснодарский краевой) авто-сабмит накапливает блокировку на IP — для них только подсказка
человеку.

## Задача 4. VPS

Российский хостинг (Timeweb, Selectel и подобные). До написания кода проверить `curl`-ом
с сервера, что суды отвечают и TLS-цепочка собирается. Сертификаты Минцифры лежат
в репозитории: `Sources/SudrfKit/Resources/RussianTrusted*.cer`.

Риск считается низким: `sudtudtestbot` уже работает на Timeweb и ходит на суды обычным
`fetch` без специального CA-бандла.

Сбор лучше держать **отдельно от сервера с боевыми делами**: массовый обход рискует
репутацией IP, и ронять адрес, с которого юристы ведут дела, не стоит.

## Задача 5. Репозиторий харвестера

Отдельный проект (`practice-harvester`), Python: `httpx` + cp1251, `selectolax`/`lxml`,
`psycopg3`, `pydantic`, `alembic`, `sentence-transformers`, `FastAPI`.

Из этого репозитория ему нужны справочники — `CourtDirectory` (9 КСОЮ + Кассационный
военный суд) и `CartotekaRegistry`. Их стоит выгрузить в JSON скриптом
`Scripts/export-directories.swift` (ещё не написан), чтобы не поддерживать два списка руками.

Порядок работ: разведка → схема БД и слой сырья → перечень → тексты → индексы → API.
Раскатка судов: 2 КСОЮ (без капчи) → 3 КСОЮ (с капчей, боевая проверка модели) →
остальные, включая `vkas.sudrf.ru`.

## Что важно не потерять

- **262-ФЗ.** Часть актов не публикуется: пустая выдача не означает отсутствия дела.
  Дела без текста должны помечаться явно, иначе база выглядит полнее, чем есть.
- **Уважительный доступ.** Троттлинг не меньше 3 с на хост, ночное окно, дневной потолок
  запросов, `robots.txt`, User-Agent с контактом, лог всех запросов.
- **Правовой режим.** Пока это личный исследовательский инструмент, вопрос не стоит.
  Перед открытием доступа третьим лицам — отдельная проверка условий использования сайтов
  судов, режима повторного распространения и остаточных персональных данных.
