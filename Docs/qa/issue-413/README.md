## Воспроизведённая причина

Оба исходных ответа разобраны неизменённым `MosGorSudCardParser` в отдельном
пакете, содержащем только SudrfKit и диагностические тесты.
SHA-256 файла парсера:
`327d837bfc46f2b455e26dedb72207973a9302d4c8d602a5f7501ca72f74983d`.

В обоих ответах собственный номер опубликован в паре `div.left` / `div.right`
с меткой «Номер жалобы ~ дела». Текущий поиск поля пропускает эту метку
и выбирает «Номер дела в суде нижестоящей инстанции».
Поле «Суд первой инстанции, судья» одновременно выбирается для собственных
`court` и `judge`. Совпадение с УИД примера сохраняется и не предотвращает
подмену реквизитов.

При построении найденной верхней инстанции номер строки выдачи сохраняется,
но суд из подробной карточки получает приоритет. Штатный парсер выдачи
не заполняет собственное поле суда. Поэтому правильный номер апелляции
сочетается с реквизитами нижестоящего суда. Прямое открытие и проверка
происхождения дополнительно могут отклонить карточку из-за неверного номера.

Диагностические проверки завершились без ошибок: отдельно одна карточка,
затем обе карточки. Они фиксируют фактически неправильный результат,
а не подтверждают правильное поведение приложения. Историческая причина
конкретной пользовательской записи без чтения этой записи не устанавливалась.

## Контрольная точка исправления

В отдельной ветке исправлены собственные поля номера, суда и судьи.
Клиент передаёт опубликованный URL для проверки собственного судебного
контекста; найденная апелляция проверяется по собственному номеру и имеющимся
УИД до подтверждения загрузки источника.

Изолированный пакет только SudrfKit прошёл класс `MosGorSudTests`:
38 тестов, 0 ошибок, включая восемь регрессий #413. Копии изменённых
исходников, теста и двух фикстур побайтово совпадали с веткой на момент
прогона. SHA-256 журнала: `f7dbbb2d7de747f227ec087bfbcc821416a2d7e9730be78d6bcef875a91fb386`.
Обычные targets приложения в этом пакете отсутствовали.

Предшествующий RED-прогон по ошибке использовал общий пакет репозитория:
он скомпилировал targets приложения, хотя выбраны были только профильные
тесты. Это не изолированный Kit-only прогон; запуск приложения и тестов
других targets не выполнялся. Последующая проверка выше использовала
отдельный ограниченный пакет. Полной проверкой приложения она не является.

Независимый review принял исправление собственных полей и сохранённого кэша;
замечание о разных временах получения двух карточек исправлено в provenance.
Изменения выбора результата, даты вступления в силу и вышестоящего номера
восстановлены до прежнего поведения. Тесты проверяют эти поля, короткое и
полное московское название районного суда и отклонение чужого суда/города.

9 октября 2026 года выбранный класс `Issue413SavedCacheNormalizationTests`
выполнен: 11 тестов, 0 ошибок. Команда:
`swift test --scratch-path /private/tmp/sudrf-413-act-projection-scratch --filter Issue413SavedCacheNormalizationTests`.
SwiftPM компилировал app/test targets как зависимости, но выполнялся только
этот класс; тесты других пакетов были исключены фильтром. Все действия
использовали синтетические карточки и отдельные временные дисковые хранилища.

Новый тест проходит через production `TrackedStorePreparation.prepare`, который
выполняет `.full`-проекцию `CourtActProjectionSynchronizer`, затем через
частичный синтетический `RefreshCenter` и production `.cases`-проекцию, после
чего открывает новое хранилище с того же URL. Проверены собственный суд,
идентификаторы дела и акта, `sourceHash`, текст и ID абзацев, а также ID,
содержимое, hash, дата создания и актуальность сохранённой сводки. Сохранены
`seenAt` и ID событий журнала. Проекция работала; AppRouter не создавался.

Журнал выбранного прогона: `/private/tmp/sudrf-413-act-projection.log`,

Это профильный результат, не полный набор тестов, CI или приёмка приложения.

Дополнительный объединённый прогон `MosGorSudTests`,
`Issue413SavedCacheNormalizationTests` и `Issue431CalendarCourtLabelTests`

Проверка чужого раздела на границе движения использует явно синтетический

`honestZero`. Это прежнее поведение не изменялось; тест с provider не доказывает
полноту настоящей поисковой выдачи.

9 октября 2026 года автор разрешил изменение вычисляемого календарного ID
при исправлении названия суда при сохранении выбранной даты, прочитанности и
постоянных ID записей/журнала. Новый профиль подтвердил `seenAt`, идентификаторы
дела/акта и журнала, но не проверял сохранение выбранного дня через
`AppRouter.reload`/обновление.

Добавлена отдельная проверка выбранного дня через настоящий callback
частичного refresh и `AppRouter.reload`. После создания router восстанавливается
исходный legacy snapshot; проверка требует составное прежнее название суда,
смену computed hearing ID после refresh и сохранение выбранного дня,
`seenAt` и постоянных ID журнала. Повторный `reload` сохраняет новый ID.
Она разрешена только при `GITHUB_ACTIONS=true` на временном hosted runner:
база и корпус временные, но стандартные настройки и системные зависимости
`AppRouter` не подменены. Локально этот сценарий пропускается до создания
router. Компиляция и локальный защитный skip пройдены; фактический переход
и согласованная визуальная приёмка ещё должны быть подтверждены.
Независимый review усиленного теста — Ship.
