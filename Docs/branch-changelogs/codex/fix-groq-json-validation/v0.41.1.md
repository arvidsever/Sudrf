# v0.41.1 — Groq structured summary correction

Roadmap: `AI-4`, `SUMMARY-5`.

## Причина

- Groq принял текущий BYOK и успешно выполнил простую синтетическую проверку,
  но два запроса реального акта завершились HTTP 400 / `json_validate_failed`.
- Старый provider payload требовал десять отдельных массивов и не задавал
  явный output budget; короткая connection probe не проверяла production-форму.

## Изменения

- Provider JSON упрощён до одного массива `items` со строгим enum раздела;
  сохранённый `ActSummary` и публичный API `SudrfKit` не меняются.
- Groq request переведён на typed DTO и фиксирует strict schema,
  `reasoning_effort=low` и `temperature=0.2`. Ненулевая temperature оставлена
  сознательно: единственный смысл повтора после `json_validate_failed` —
  получить другой sample, а расхождение с оригиналом ограничено локальной
  проверкой цитат и защищённых реквизитов.
  Запланированный резерв `8192` при ручной проверке был немедленно отклонён
  free-tier лимитом как HTTP 413 / `rate_limit_exceeded`.
  Резерв вывода считает `GroqTokenBudget`: оценка входа (2 символа на токен плюс
  служебные токены prompt и схемы) вычитается из рабочей части минутного
  бюджета, остаток идёт под вывод, но не более `4096`. Если полезного места не
  остаётся, поле не отправляется и действует server-side completion cap Groq.
  Порог по символам с фиксированным резервом не используется: он заведомо
  допускал запросы, у которых вход вместе с резервом превышает минутный лимит,
  то есть менял `json_validate_failed` на неповторяемый HTTP 413.
  Groq chunk остаётся 18000 символов: акт на 7564 input tokens помещается в
  контекст одним запросом, но вместе с completion превышает бесплатный минутный
  token budget. Уменьшение chunk не решает лимит без минутной паузы: второй
  последовательный запрос получил 429 / `Retry-After: 51`.
- Обрезанный ответ распознаётся по `finish_reason=length` отдельной ошибкой и не
  тратит повтор: без этой проверки он приходил как невалидный JSON.
- HTTP 413 получил собственное сообщение вместо безликого «AI API вернул HTTP …».
- Prompt ограничивает количество выводов и длину evidence quotes.
- `json_validate_failed` распознаётся только по allowlisted machine code.
  Повтор разрешён лишь тогда, когда два запроса подряд укладываются в минутный
  token budget: на крупном chunk он всё равно упёрся бы в лимит и отнял бы
  бюджет у остальных chunks. Произвольный HTTP 400 не повторяется.
- Raw provider message, `failed_generation`, prompt и HTTP body не попадают в
  ошибку, UI или логи. Сообщения об ошибках не называют вендора внутри
  провайдер-независимого `AISummarizerError`.
- Connection probe использует многоабзацный синтетический акт и отклоняет
  пустую либо невалидную сводку.
- Groq cache identity повышена до `groq-act-summary-v2` /
  `summary-pipeline-v2`, и теперь она действительно инвалидирует кэш: staleness
  сравнивает не только hash источника, но и `promptVersion`/`pipelineVersion`.
  Когда текущая конфигурация недоступна (нет ключа или согласия), сравнивается
  только hash — перегенерировать сводку всё равно нельзя.
- Словарное представление schema больше не содержит `preconditionFailure` в
  production-пути: оно нужно только проверкам формы.

## Правки по adversarial review

- Порог `sourceText.count > 12_000` с фиксированным резервом `4096` заменён на
  расчёт от минутного бюджета: при 8K TPM резерв 4096 оставлял входу менее 3904
  токенов, куда 12 000 символов русского текста не помещаются ни при какой
  токенизации. Акты примерно от 9–10 до 12 тыс. символов гарантированно
  получали pre-inference HTTP 413, который не повторяется, — то есть акты
  среднего размера отказывали жёстче крупных.
- Добавлена проверка `finish_reason`: обрезанный ответ больше не выглядит как
  невалидный JSON и не тратит повтор.
- Повтор после `json_validate_failed` перестал быть безусловным: идентичный
  запрос на крупном chunk не укладывается во второй проход минутного бюджета.
- Заявленная cache identity доведена до фактического поведения: staleness
  сравнивает `promptVersion` и `pipelineVersion`, а не только hash источника.

## Проверки

- `swift test` — 536 тестов пройдены полностью 30.07.2026 на состоянии до правок
  по review, включая `AISummaryPipelineTests`, `CorrectivePassTests` и системные
  CoreML/Vision-проверки. Правки по review проверяются CI-линиями
  `build-test`, `build-test-xcode-27` и `package-app`.
- `swift build --product SudrfApp`, `swift build --product sudrf-cli` и локальная
  Xcode-схема Sudrf — успешно.
- Strict-schema shape, section mapping, hostile metadata, безопасная ошибка,
  retry budget и connection probe покрыты регрессионными тестами.
- Добавлены тесты: инвариант «оценка входа + резерв ≤ минутный бюджет» на всём
  диапазоне длин, резерв для акта среднего размера, распознавание
  `finish_reason=length` без повтора, отсутствие повтора `json_validate_failed`
  на крупном chunk и staleness после смены prompt/pipeline.
- Реальный Groq BYOK: усиленная синтетическая проверка прошла с HTTP 200 и
  валидной cited summary.
- Тот же реальный акт больше не вернул `json_validate_failed`, но ручной прогон
  упёрся в отдельный free-tier TPM limit: 429 / `Retry-After: 50–52`. Проверка
  HTTP 200 и переходов по ссылкам остаётся ручным blocker для review; приложение
  не выполняет скрытое ожидание дольше 15 секунд и не запускает бесконечный
  retry.

## Review gate

- До передачи коллеге в PR публикуется AI self-review с privacy, retry,
  cache-invalidation и manual-test ограничениями.
- Adversarial review выполнен на `babfb00`; его замечания исправлены в этой
  ветке отдельным коммитом.
- Ручное подтверждение HTTP 200 на длинном реальном акте и переходов по
  ¶-ссылкам остаётся ограничением free tier: минутный token budget, а не
  structured output. Код не маскирует лимит скрытыми паузами и повторами.
