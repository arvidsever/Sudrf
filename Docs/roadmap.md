перед мёрджем.

`Docs/AI-ROADMAP.md`: выполненные этапы сохранены как история, незавершённые встроены в

### Правила SemVer

- Новая пользовательская функция или новый источник данных повышают второй сегмент и сбрасывают третий в ноль.
- Исправления, косметические изменения, переобучение без новой продуктовой возможности и developer-only инструменты повышают третий сегмент.
- Каждая влитая ветка получает собственный номер, выбранный по этим правилам; отсутствие отдельной сборки не является основанием объединять заметки.

**ФССП #113 работает end-to-end с production-распознаванием CAPTCHA.** Для каждой строки
исполнительного документа поиск идёт независимо по опубликованному судом электронному ИД,
а при его отсутствии — по номеру бумажного листа; регион не ограничивается, чтобы не
потерять переданное производство. Точное совпадение хранит официальные поля ФССП рядом с
независимым результатом Казначейства. CAPTCHA и ошибка одного источника не стирают
последний успех другого. Автор визуально подтвердил живой сценарий
`11RS0001#2-9143/2025#1`: найдено ИП `587893/26/98078-ИП`, предыдущий номер и
подразделение совпали с официальной выдачей; второй ИД независимо получил «не найдено».

В 0.45.0 отдельная CoreML-модель ФССП прошла неизменённый production-gate: 4 000
подтверждённых сервером PNG, 30 вручную проверенных фикстур, 97,2% полных ответов на
независимом экзамене и 99,7% точности у 373 ответов с уверенностью не ниже 90%. Поток
получает свежий challenge на каждой из максимум трёх попыток, а затем оставляет ручной
fallback. Модель опубликована отдельным release asset; чистая CI-сборка проверяет SHA-256,
eligibility-отчёт и наличие модели внутри `.app`.

**Числовая CAPTCHA СОЮ в 0.45.0 переобучена на 16 228 визуально проверенных PNG.** Две
компактные CoreML-модели работают ансамблем: приложение выбирает более уверенный ответ.
На независимом экзамене полностью распознано 91,4% CAPTCHA и 98,2% отдельных цифр; все
известные регрессионные изображения распознаны без ошибок. Обе модели доставляются
отдельными release assets и вместе проверяются в упакованном приложении.

**#124 закрыт в 0.45.1 строгим allowlist заседаний.** Время и текст результата больше не
служат положительными признаками: общий предикат lifecycle, «Обзора», календаря и ленты
смотрит только на подтверждённые формулировки поля `event`. Результат по-прежнему нужен
только для исключения уже завершённых заседаний из будущих; миграция данных не требуется.

**#118 закрыт в 0.45.3 числовым порядком мировых участков.** `MagistrateCourt.number`
берёт номер из фиксированного классификационного кода (`11MS0001` → `1`), а
`SearchModel` передаёт его в уже существующий общий сортировщик. Участки идут как
№ 1, № 2, № 10, № 100; некорректные коды и ненумерованные суды сохраняют алфавитный
fallback.

**#127 закрыт в 0.45.4 удалением ошибочной английской локализации.** Девять русских
source strings в `Localizable.xcstrings` имели `en`-переводы, поэтому macOS показывала
`Open case` и другие английские подписи. Английские юниты удалены; каталог и development
region остаются русскими, без дублирования source strings и без лишнего `knownRegions`.

**#112 закрыт в 0.45.5 привязкой судьи к каждому делу в календаре.** В grouped-блоке
судья теперь показан компактной подписью в той же строке, что время и номер дела, а общий
footer содержит только общие реквизиты суда и помещения. Конфликтные и одиночные блоки
сохраняют прежний состав данных; высота блоков и позиции на временной сетке не изменены.

**#114 закрыт в 0.46.0 удалением пользовательских подборок.** Действие доступно в
контекстном меню подборки и всегда требует подтверждения с числом дел. Удаляется только
членство дел в подборке: сами дела остаются отслеживаемыми, активный фильтр возвращается
к «Все дела», счётчики перестраиваются, а Spotlight обновляется только для затронутых дел.
Системную строку «Все дела» удалить нельзя; пустые подборки удаляются тем же действием.

**TestFlight в 0.45.2 больше не является отдельной линией разработки.** Sandbox,
миграция прежнего контейнера и полный набор production-моделей CAPTCHA влиты в `main`.
Каждая следующая сборка для тестировщиков архивируется из актуального `main` с новым
номером build; постоянная ветка `testflight` не используется. Проверка Xcode-сборки
сверяет SHA-256 всех трёх моделей и eligibility-отчёт внутри фактического `.app`.

**Исполнение в Казначействе #150 завершено сквозным контуром.** Карточка суда извлекает
все строки таблицы исполнительных документов, общий блок «Исполнение» стоит в конце
карточки, а для отслеживаемых дел бумажные листы автоматически проверяются через RSS и
прямую страницу Казначейства. Сохраняются точный официальный статус, орган, подразделение
и история по устойчивым `guid`; not found, ambiguous, terminal и ошибки источника не
стирают последний успех и повторно проверяются по общему TTL. Электронные ИД и бумажные
листы, явно направленные приставам, уже показаны как ФССП, но не отправляются в
Казначейство. Live-кейс `2-8236/2025` подтвердил три независимых бумажных результата,
включая восемь этапов для `ФС № 049377165` (`documentId=2902695`).

**Spotlight в 0.42.33–0.42.34 проверен обоими путями.** Встроенный поиск возвращает дела по
«декабрист», а системный Spotlight видит Sudrf и показывает его записи при фильтрации по
приложению. Общая выдача ранжирует их ниже контактов и файлов — это системный рейтинг, не
потеря индекса. Production-путь теперь использует именованный `CSSearchableIndex` и
`CSSearchableItem` со связанным `IndexedEntity`: так записи остаются доступны во время
известного сбоя `indexAppEntities` / «Failed to request donation» в macOS 27 beta. Записи
получают `expirationDate = .distantFuture`, а переход с manifest v4 на v5 один раз полностью
перестраивает старый индекс, чтобы прежние записи тоже получили новый срок.

## Что показал опыт

Восемь из тринадцати задач потянули находки, которых не было в issue. Трижды это был
фоллаут собственной правки (смена `feedID` воскрешала прочитанные записи ленты; смена
подписи суда ломала поиск по суду первой инстанции; retention сроков заставлял колонку
врать «все сроки подтверждены») — чинилось в том же PR. Дважды — соседний дефект,
вынесенный отдельно (#118, #124). В #102 находка пришла из фикстур: последний раздел
рубрикатора категории часто оказывается заглушкой («иные…», «прочие…»), и наивная свёртка
до последнего раздела дала бы «иные споры по делам о восстановлении на работе» вместо
«Дела о восстановлении на работе». Разделителя в живых карточках два — `→` и `->`.

### `DATA-1` — единый слой сущностей

1. До изменения схемы ввести `VersionedSchema` и явный migration plan, сделать
   проверяемый бэкап файлов persistent store (`store`, `-wal`, `-shm`) и при
   ошибке показать блокирующий экран восстановления. Тихая рабочая сессия в
   in-memory fallback запрещена. Marker и каталог backup выводятся из текущего
   `VersionedSchema.versionIdentifier`; если неполной оказалась ранее созданная резервная
   копия, именно она сохраняется в quarantine, после чего создаётся новая проверенная
   копия. Существующая пользовательская база автоматически в quarantine не перемещается:
   это допустимо только по явному действию из #144.
   Переход V1→V3 намеренно проходит последовательно через lightweight-stage V2;
   V2 была внутренним промежуточным состоянием PR и публично не выпускалась.
2. Оставить `TrackedCaseRecord` источником отслеживания, `movementData` —
   источником движения.
3. Добавить перестраиваемую SwiftData-проекцию `CourtActRecord`. `sourceActID`
   считается нестабильной подсказкой, а не гарантией портала. Логический ID
   назначается версионированным алгоритмом и сохраняется: exact source match →
   уникальный semantic match (дело/инстанция/суд/вид/дата) → уникальный
   `sourceHash` → новый deterministic ID. Исправление текста меняет
   `sourceHash` и инвалидирует сводку, но по возможности сохраняет document ID.
4. Вынести общий `ModelContainer`; добавить `CaseCatalog` actor, возвращающий
   только `Sendable`-снимки.
5. `ActParagraphizer` становится единственной границей сегментации и поглощает
   соответствующую логику `CourtActFormatter`; экран, PDF, Spotlight и AI не
   имеют независимого повторного разбиения.
6. Хранить `paragraphizerVersion` и snapshot границ/текстов абзацев вместе с
   актом и сводкой. Обновление алгоритма не перенумеровывает старые цитаты;
   новый snapshot строится только для новой ревизии `sourceHash`.
7. Сохранение основной записи и её проекции остаётся одной транзакцией.
   Refresh, upsert и CAPTCHA перестраивают только затронутое дело; repair удаляет
   старые ключи и строит новый. Полный rebuild остаётся для bootstrap,
   восстановления и явной команды. Если непустой `movementData` не декодируется,
   последняя проекция и сводки сохраняются до успешного обновления; повреждение
   нельзя трактовать как удаление актов.
8. Persistent bootstrap выполняет backup, migration и полную подготовку
   проекции до создания `AppRouter` и вне MainActor. Первый кадр всегда loading;
   при ошибке рабочий UI и mutation paths не становятся доступны.

Критерий: существующая база мигрирует без потери данных, а ID, хеши и номера
абзацев стабильны между запусками.

### `AI-4` — универсальная AI-инфраструктура

Базовый интерфейс:

```swift
protocol ActSummarizing: Sendable {
    func summarize(
        document: ActDocument,
        options: SummaryOptions
    ) async throws -> ActSummary
}
```

1. `ActSummary` хранит требования, позиции сторон, обстоятельства, мотивировку,
   резолютивную часть, суммы, даты, сроки, обжалование, предупреждения и ссылки
   на исходные абзацы.
   Предупреждения модели являются теми же cited claims и проходят общую
   валидацию. Provider payload — отдельный тип без `localWarnings`, английской
   диагностики и pipeline flags; эти поля назначает только приложение, в том
   числе для провайдеров без strict JSON Schema.
2. В текущем личном пилоте реализовать только `MockActSummarizer` и Groq BYOK с
   фиксированной моделью `openai/gpt-oss-120b`; Apple подключается тем же
   протоколом как экспериментальный путь. GigaChat и YandexGPT остаются будущими
   benchmark-кандидатами и не входят в настройки, factory или provider adapters
   PR #42. Их добавление допускается только отдельным PR после official-docs gate
   и сравнения качества/географической доступности.
   Каталог [`nejib1/Free-LLM`](https://github.com/nejib1/Free-LLM) используется
   только для discovery кандидатов: сам
   README прямо предупреждает, что тарифы и лимиты меняются еженедельно. Перед
   добавлением каждого нового адаптера обязательна перепроверка по официальным docs:
   фиксируемый model ID, structured JSON/schema, контекст, доступность из РФ и
   региона разработчика, privacy/retention и условия free tier. Community
   routers и провайдеры без понятного оператора/политики обработки судебных
   актов не допускаются. OpenRouter free-router не используется. Google AI
   Studio, Cerebras и Mistral можно включить в benchmark опубликованных актов только
   после этого gate; локальные Ollama/LM Studio из списка рассматриваются как
   прототипы, а production local-путь для macOS остаётся MLX/Core ML.
3. Первый личный прогон фиксирует Groq BYOK и `openai/gpt-oss-120b`: Settings →
   AI содержит Keychain, проверку соединения, облачное согласие и подготовку
   Apple через английский. Выбор провайдера и автоматический режим возвращаются
   только после сравнительного benchmark.
   На 20 июля 2026 года официальная документация Groq подтверждает strict
   structured outputs для этой модели:
   <https://console.groq.com/docs/structured-outputs>. Model ID не выбирается
   через случайный router.
   Первый полевой прогон выявил два `json_validate_failed` на реальном акте при
   успешной синтетической проверке ключа. Corrective-путь использует компактный
   provider payload `items[]` с enum раздела, `reasoning_effort=low`, выводимый
   output budget и не более одного повтора на chunk. Полевой connection probe
   показал, что резерв `8192` output tokens немедленно отклоняется free-tier
   лимитом Groq как HTTP 413 / `rate_limit_exceeded`: минутный token budget
   списывает резерв ещё до инференса.
   Поэтому резерв не задаётся порогом по символам — такой порог при
   фиксированном резерве заведомо допускает запросы, которые не укладываются в
   бюджет. `GroqTokenBudget` оценивает вход (консервативно 2 символа на токен
   плюс служебные токены prompt и схемы) и отдаёт остаток бюджета под вывод,
   не более `4096`; если полезного места не остаётся, поле не отправляется и
   действует server-side completion cap Groq. Обрезанный ответ распознаётся по
   `finish_reason=length` отдельной ошибкой, а не как невалидный JSON.
   Немедленный повтор после `json_validate_failed` разрешён только тогда, когда
   два запроса подряд укладываются в тот же минутный бюджет: на крупном chunk
   повтор всё равно упёрся бы в лимит и отнял бы бюджет у остальных chunks.
   Groq chunk остаётся 18000 символов: проверочный акт на 7564 input tokens
   помещается в контекст одним запросом, но вместе с completion превышает
   бесплатный минутный token budget. Искусственное дробление не решает это без
   минутной паузы между частями: второй chunk получает 429. Это отдельное
   ограничение free tier, не возврат `json_validate_failed`; PR не маскирует его
   бесконечными повторами и не ослабляет structured output.
   Из HTTP body разрешено извлекать
   только allowlisted machine code; provider message и failed generation не
   сохраняются и не выводятся. Проверка соединения обязана получить непустую
   cited summary для многоабзацного синтетического акта.
   Смена `promptVersion` или `pipelineVersion` делает сохранённую сводку
   устаревшей наравне с изменением текста акта: staleness сравнивает и hash
   источника, и идентичность prompt/pipeline.
4. Фиксировать model IDs; не использовать случайный free-router.
5. Benchmark на 50–100 уже опубликованных и обезличенных судом актов хранится
   вне Git; в Git остаются runner и синтетические фикстуры. Повторное
   обезличивание не выполняется: проверяется реальный опубликованный текст.
   Полный benchmark вручную, не в CI.
6. Согласие на внешний cloud уже в личном BYOK-режиме явно предупреждает об
   отправке ФИО и иных персональных данных третьих лиц.

Порог допуска: 100% существующих paragraph-ссылок, не менее 95% правильных
критических реквизитов и 90% полноты обязательных разделов.
Методика, формат фикстур и границы ручного корпуса остаются в
[`Docs/AI-BENCHMARK.md`](AI-BENCHMARK.md); это проверочный материал, а не второй roadmap.

### `SUMMARY-5` — сводка одного акта

2. Короткий акт обрабатывать одним typed/structured запросом; длинный —

   не более двух provider-вызовов: один исходный и максимум один повтор либо
   после validation failure, либо после кратковременного 429/5xx. `Retry-After`
   принимается не более 15 секунд; более длинный лимит завершается понятной
   ошибкой. Итоговая объединённая сводка проверяется против полного документа
   без повторной генерации всех чанков. Дословность чувствительна к регистру
   (нормализуются только пробельные символы), а критические реквизиты ищутся с
   границами токенов внутри каждого процитированного абзаца отдельно. Формы
   календарной даты сопоставляются по day/month/year: словесный месяц может быть
   подтверждён числовой датой, но не другим месяцем или годом.
4. Ссылки переходят к оригинальному абзацу с подсветкой.
5. `ActSummaryRecord` хранит provider/model/promptVersion/pipelineVersion,
   `sourceHash` и `generatedAt`; при смене текста сводка устаревает.
6. Всегда показывать предупреждение о проверке по оригиналу.

### `APPLE-6` — Apple Foundation Models и двойной перевод

Режимы: Apple с русским напрямую; Apple через английский (Experimental);
внешний BYOK.

Прямой путь используется только при доступности модели и официальной поддержке
русского locale.

Переводной путь сначала имеет статус spike с go/no-go по отдельному
мини-benchmark. Полный production pipeline ниже реализуется только при `go`.

Spike проверяет загрузку языковой пары, сохранность paragraph/literal IDs,
качество ru→en→summary→ru и реальную вместимость chunk pipeline на нескольких
коротких и длинных актах.

Разрешение на загрузку языков запрашивается только через привязанную к Settings
SwiftUI `translationTask`, последовательно для ru→en и en→ru. Генеративный actor
создаёт headless-сессии только для уже установленных языков и проверяет
`isReady`; UI-сессия за пределами lifetime View не сохраняется. Literal IDs
сравниваются как multiset: грамматическая перестановка разрешена, потеря,
дублирование и подмена отклоняются.

До решения `go` английская сводка валидируется против переведённых абзацев, но
русская citation указывает на исходный абзац целиком: надёжного обратного
сопоставления короткой английской цитаты с русским фрагментом spike пока не
обещает. UI-метка Experimental и обязательная проверка оригинала сохраняются.

Production-путь после `go`:

1. Проверить и при необходимости загрузить пару русский ↔ английский через
   Translation framework.
2. Извлечь из русского оригинала защищённые литералы: номера дел/УИД, даты,
   сроки, суммы, валюты и нормы права; назначить им стабильные IDs.
3. Перевести абзацы batch-запросом, сохраняя paragraph IDs вне переводимого
   текста.
4. Получить строгую английскую `ActSummary` от Apple.
5. Перевести обратно только человекочитаемые поля; JSON-ключи, IDs и реквизиты
   через перевод не пропускать.
6. Подставить оригинальные русские литералы, привязать выводы к русским
   абзацам и выполнить локальную проверку.
7. Показывать индикатор двойного перевода и диагностическую английскую сводку.
8. Кэш учитывать OS build, языковую пару и версию pipeline.

До сравнительного benchmark рабочий пользовательский маршрут зафиксирован на
Groq BYOK / `openai/gpt-oss-120b`. Apple напрямую и через английский существуют
как изолированные экспериментальные адаптеры и не подменяют рабочий провайдер.
После benchmark планируемый автовыбор: Apple напрямую → Apple через английский,
если эксперимент включён → победивший BYOK → понятное сообщение о недоступности.

`APPLE-6` не становится `completed` вместе с merge PR #42: для этого обязателен
ручной translation go/no-go на macOS 26 и macOS 27. Этапы `S6-0B`–`SUMMARY-5`
исторически получили `completed` после своих записанных проверок; незавершённым системным
gate остаётся только APPLE-6 и его отдельные runtime follow-ups.

## Ближайшая очередь

Очередь ниже заменяет прежнее разбиение между обычным и AI-roadmap. Внутри волны задачи
можно вести параллельно только там, где явно нет стрелки зависимости.

### 1. Сохранность данных: #77 + #44 → #144 + #64

**#77** как P0 проверяет startup/store-selection boundary: обычный relaunch не может
выглядеть как новая пустая база. Независимо от диагностики **#44** сразу устраняет
подтверждённый ложный успех после rollback. Затем **#144** даёт retry и только явный
обратимый карантин всех `store`/`-wal`/`-shm`, а **#64** делает durability-critical commit
явно fallible во всех mutation paths. Зависимости внутри волны: #77 → #144 и #44 → #64.

### 2. Correctness и source gate перед event journal

**#56** — ближайшая юридическая регрессия: ложный срок при живой кассации. **#187**
отдельно возвращает прошедшие заседания в календарную проекцию, сохраняя строгий allowlist
и future-only поведение ближайшего заседания/App Intent.

Для пригодного normalized input закрыть source-specific gate фазы A. Рекомендуемый, но не
технически последовательный порядок: **#79/#78** (unknown против honest zero),
**#82/#88/#164** (CAPTCHA continuation/session), **#89** (движение КСОЮ). Первый уровень
**#181** — raw response → normalized snapshot/outcome — добавляется в PR соответствующих
source fixes как merge-gate и сам по себе #181 не закрывает.

### 3. Единый event contract: #181 level 1 → #155 → #179 → #181 level 2

После source fixtures **#155** вводит shadow journal со стабильной event identity без
переключения UI. После фактической shadow-сверки **#179** переводит ленту, локальные
уведомления и badges на journal. Второй уровень **#181** — old/new snapshot → ожидаемые
`CaseEvent[]` — фиксирует стабилизированный vocabulary; отдельная ветка #181 собирает оба
уровня в законченный contract и только тогда закрывает issue.

### 4. Юридическая семантика: #70 + #129 + #125 + #111 → #128

**#56** должен быть закрыт до начала **#70**. Rules engine подключается к event contract и
включает накопленные deadline cases
**#129/#125/#111**: календарные месяцы, исключение нерабочих дней из срока и перенос
окончания остаются разными правилами одного календаря и зависят от процессуального
кодекса. Эти три задачи ждут #70, чтобы формулы и provenance не реализовывались сначала в
legacy-ветках, а затем повторно в rules engine. Закрытый #80 остаётся negative fixture, а
его незавершённая live-проверка входит в acceptance #70. Только после развязки стадии и
срока исправляется **#128**.

### 5. Пользовательские проекции: #101 + #133 и #148

**#101 + #133** делать одним заходом после #179: стороны, суд и номер форматируются поверх
единого события, а не закрепляют ещё один presentation-only контракт. Односторонняя
проекция Sudrf → Apple Calendar **#148** строится после #179 и #70 поверх стабильной event
identity и deadline semantics. Изменения `EKEvent` не меняют судебное состояние Sudrf.

### Параллельный system-acceptance gate: #43 + #46 + #186 → #66

Эта дорожка не блокирует начало #155 после завершения data/source gates, но блокирует
CASEAI-7. До закрытия APPLE-6 устранить несвежую сводку при refresh **#43**, проверить
cold-start App Intents **#46** и конфликт Debug/Developer ID Spotlight identity **#186**.
После этого **#66** проводит ручную матрицу macOS 26/27, Apple Silicon/Intel, языковых
пакетов, clean install/upgrade, recovery непустой базы, consent и fallback и принимает
go/no-go двойного перевода. Merge адаптеров сам по себе APPLE-6 не закрывает. **#45**
остаётся отдельной rendering reliability-задачей, но CASEAI-7 не блокирует.

### 6. Следующие продуктовые линии

- **CASEAI-7** — после #66, #155/#179, #70 и устранения #43: сначала
  детерминированное «Что изменилось», затем история инстанций, retrieval по делу, digest
  и command bar.
- **#180 scheduler** — только после #87 и измерений #68/#65; если baseline не показывает
  starvation или лишнюю нагрузку, закрыть отчётом без нового scheduler.
- **#69 Developer ID/notarization** остаётся открытой: сертификат, export и hardened
  runtime проверены, но нужны notary credentials, submission, stapling и release job.
- **#149 backend/APNs** — после #155/#179, базовой source reliability и результатов
  #87/#68; технически не зависит от #148, но предшествует PUBLIC-8.
- **PUBLIC-8** — после CASEAI-7, APPLE-6, #69 и #149. BYOK
  сохраняется, публичный cloud требует proxy, квот, privacy/legal review и запрета
  хранения текстов.
- **Новые source families #106 → #107 → #108** — после стабилизации adapter/fixture/event
  contract; не раньше source reliability и основных пользовательских цепочек.

## Архитектурные решения автора — 23.08.2026

**#155 — поднять в высокий приоритет.** После ближайшего блока correctness/data-safety,
не дожидаясь закрытия всего накопленного UI/reliability backlog, реализовать #155 в shadow
mode. Следующие крупные функции по возможности строить уже поверх event journal, а не
размножать текущие независимые эвристики изменений.

**#148 Apple Calendar — первая версия только Sudrf → Calendar.** Судебное состояние и
`CaseEvent` остаются source of truth. Изменение или удаление `EKEvent` пользователем не
меняет snapshot/CaseEvent; Calendar — проекция. Двустороннюю синхронизацию в первый scope
не включать. Если позже понадобятся пользовательские заметки/override, хранить их отдельным
локальным слоем, не смешивая с данными суда.

**#149 сервер + APNs — обязательная часть продукта, но позже.** Это не условная задача
«если локального background refresh окажется мало»: always-on backend точно строим, но
только после стабилизации локального event contract #155 и базовой source reliability.
Сервер не заводит вторую доменную модель: он воспроизводит/потребляет те же normalized
snapshots и semantic `CaseEvent`, а затем масштабирует scheduling/delivery.

registry лучше делать generic, чтобы тот же сигнал мог помочь #87, но первая
product-функция #156 остаётся узкой и проверяемой.

## Архитектурная дорожка из open-source review

Подробная фиксация: `Docs/architecture/open-source-reference.md` и
`Docs/architecture/reference-alexxmirny-sudrf-parser.md`.

Главный вывод — **не менять стек**, а сделать явными контракты между уже существующими
слоями. Целевая цепочка:

`transport → source adapter → normalized snapshot → identity/reconciliation → semantic diff → append-only CaseEvent journal → projections`.

### Архитектурные invariants

- **Swift/SwiftUI/SwiftData остаются.** SwiftData не менять без измеренного bottleneck;
  сначала добавить логические сущности snapshot/event/refresh-attempt и нормальные
  миграции.
- **HTTP-first.** `URLSession` + cookies/session continuity + CP1251 + trust roots +
  throttle/retry/backoff — штатный transport. Selenium/Puppeteer/browser automation —
  только fallback для источника, который объективно нельзя получить обычным HTTP. Для
  `msudrf` #164 это означает сначала реализовать KCAPTCHA как HTTP session-unlock, а не
  сразу переносить Puppeteer/WKWebView-подход референсов.
- **Transport не знает процессуальной семантики.** Его ответственность: HTTP, redirects,
  charset, TLS, cookies, throttling, retry, CAPTCHA continuation, host health. CAPTCHA
  protocol при этом может быть token-based или session-based — транспорт обязан сохранить
  это различие, а не свести всё к фиктивному `captchaid`.
- **Source adapter не знает UI.** Он строит URL, классифицирует response, извлекает
  source-native identity и нормализует listing/detail в общую модель. По мере добавления
  #106/#107/#108 вводить capabilities/adapter registry вместо разрастающихся `if source`.
- **Domain не зависит от presentation.** Identity/reconciliation, стадии, сроки и semantic
  diff живут вне View/notification formatter.
- **Номер дела — атрибут, не primary key.** Court identity — официальный код, где он
  надёжен; карточка/производство — УИД либо source-native ID, scoped по court/source;
  logical case — граф связанных карточек. #94/#132/#156 — обязательные regression cases.
- **Последний хороший snapshot не стирается плохим fetch.** HTTP 200 stub, CAPTCHA,
  partial/unknown response и parse error — отдельный refresh outcome, а не новое пустое
  состояние дела.
- **Raw JSON diff запрещён как пользовательская семантика.** `alexxmirny/sudrf_parser`
  полезно подтверждает модель snapshot→diff→notification, но его positional array diff
  — negative reference: перестановка строк/косметика не должны создавать события.
- **Все downstream-проекции читают один event contract.** Лента, локальные notifications,
  badges, Spotlight, Calendar и будущий APNs не сравнивают snapshots самостоятельно.

### Фазы и gates

**A. Надёжный source state до semantic events: контракт #177 завершён в 0.46.2;
source-specific gates продолжаются.**

Закрыть/стабилизировать source correctness и partial-state кейсы, которые могут сделать
новый snapshot ложным: #82/#88/#89/#164, #79/#78 и связанные фикстуры.
Не требуется ждать всех UI/reliability issues; нужен именно пригодный normalized input.

Для `msudrf` gate включает не только распознавание `kcaptchaForm`, но и проверяемый
continuation contract: challenge page → `/captcha.php` → POST `captcha-response` →
session unlocked → исходный listing, всё в одной cookie session. CAPTCHA failure не равна
нулевой выдаче.

Gate: один и тот же response детерминированно даёт usable normalized snapshot,
operation-specific honest-zero outcome либо явный partial/error outcome; не существует
пути «плохой HTML → пустой valid snapshot».

Реализация #177 использует общий `SourceOutcome` до persistence: полный snapshot,
honest zero, partial, CAPTCHA, maintenance, transport и parser failure имеют разные
типизированные исходы. Последний безопасный `SourceAttempt` хранится отдельно от
`movementFetchedAt`; partial применяет только пригодную часть через существующий
`MovementCachePolicy`, но не продлевает TTL полного успеха. Runtime CAPTCHA URL остаётся
в памяти и не попадает в сохраняемый provenance.

**B. #178 — identity/reconciliation и discovery evidence: завершено в 0.46.3.**

Использовать official court code + УИД/source-native IDs и хранить смену display number как
историю identity, а не как новое несвязанное дело. #156 добавляет `r_juid` как независимый
registry/evidence source для передачи по подсудности; #87 использует те же reconciliation
правила при фоновом discovery. Manual и periodic discovery обязаны сходиться к одной цепочке.
#178 реализуется вместе с regression-stories #94/#132/#156, а не после их отдельных
one-off identity paths.

Gate: повторное обнаружение той же карточки другим маршрутом не создаёт дубль; новая
карточка с новым номером может быть связана без опоры на строковое равенство номера.
#155 потребляет identity карточки из #178, но остаётся владельцем identity событий.

Реализация хранит отдельный UUID логического досье, точные source-native карточки,
историю номеров и несколько судебных УИДов с provenance. Совпадение полного структурно
корректного судебного УИДа достаточно для объединения карточек; новый УИД присоединяется
только по официальной predecessor/registry/source-native связи. `case_uid` портала
хранится отдельно и никогда не сравнивается с судебным УИДом. Ручное добавление,
background refresh и repair прежней базы проходят через один reconciler; V5 → V6
сохраняет неизменяемый technical key и старые адреса как aliases.

**C. #155 — shadow `CaseSnapshot → CaseEvent`.**

**Приоритет подтверждён автором 23.08.2026:** эту фазу брать сразу после ближайшего блока
correctness/data-safety, не дожидаясь закрытия всего UI/reliability backlog.

Сохранять последний normalized snapshot и append-only journal, но первое время не менять
действующую ленту. На каждом refresh считать semantic events параллельно и сравнивать с
текущим поведением. Event ID стабилен между relaunch/refetch и пригоден для дедупликации
локального и будущего серверного notification path.

Gate: identical snapshot → 0 events; reordering/whitespace/publish timestamp → 0 events;
новое заседание/акт/инстанция → ровно одно событие; partial fetch → 0 ложных cancel/delete.

**D. #179 — Event journal становится источником пользовательских изменений.**

После shadow-сверки перевести на journal ленту и локальные notifications, затем badges и
прочие производные. Старые presentation strings не участвуют в event identity. Историю
не пересобирать заново при изменении formatter, иначе старые уведомления «воскреснут».

**E. #70 подключается как юридическая семантика поверх того же contract.**

Rules engine владеет формулой срока, trigger/evidence и provenance; #155 владеет общей
семантикой события/dedup/projections. Deadline lifecycle (`proposed/confirmed/changed/
expired/superseded` — финальный vocabulary определить в #155/#70) не заводит отдельный
feed-specific ID.

**F. #148 Calendar — односторонняя projection, не второй database.**

**Решение автора 23.08.2026:** первый scope — только Sudrf → Apple Calendar. После event
identity маппинг `CaseEvent/event state ↔ EKEvent` становится технически прямым: перенос/
отмена обновляют существующий Calendar event. Обратное изменение `EKEvent` не меняет
судебное состояние в Sudrf; двустороннюю синхронизацию в этот этап не включать.

**G. #180 — refresh health, scheduler и canary после устойчивой семантики state/event.**

#87/#68/#65 должны различать `lastAttempt` и `lastSuccess`, не считать partial успешным
refresh и давать evidence, почему источник не обновился. Только после этого имеет смысл
адаптивный scheduler: приоритет по близости заседания/срока, свежим изменениям, ожиданию
higher instance, предыдущим ошибкам, TTL и недавнему открытию пользователем; для внешних
сбоев — exponential backoff + jitter и при необходимости host circuit breaker.

#180 заведён заранее как evidence-first backlog, но реализация начинается только если
измерения после #87 и host-health instrumentation из #68 подтвердят starvation или лишнюю
нагрузку простого TTL. Полный Diagnostics UI #68 scheduler не блокирует. Если проблема не
подтвердится — issue закрывается отчётом без новой очереди.

**H. Новые source families — поверх contract, а не рядом с ним.**

#106 Москва → #107 СПб → #108 общий модуль. Новый источник обязан дать capabilities,
source identity, normalized snapshot и fixture suite; UI не получает новый `if Moscow`
или `if magistrate`, если различие можно выразить adapter capability.

**I. #149 backend — обязательный поздний этап того же contract.**

**Решение автора 23.08.2026:** always-on backend и APNs точно входят в продукт, но позже.
После стабилизации #155 и базовой source reliability сервер масштабирует ingestion/
scheduling/delivery, не вводя вторую модель дела и второй diff-engine. Local refresh и
backend должны выдавать совместимые event IDs/semantics, чтобы одно изменение не приходило
пользователю дважды. PostgreSQL/Redis/queues/search index появляются только при серверной
нагрузке, которая их обосновывает; в desktop их нет.

### #181 Fixture/test contract

Для каждого важного portal family нужны **два независимых уровня regression fixtures**:

1. `HTML/response → normalized snapshot`;
2. `old snapshot + new snapshot → expected CaseEvent[]`.

Постоянный pathology corpus: CP1251; canonical/alternate host; CAPTCHA и post-CAPTCHA
session; **`msudrf` KCAPTCHA (`kcaptchaForm` + `/captcha.php` + POST + cookie continuity)**;
maintenance/error page с HTTP 200; honest zero-results против unknown; duplicate rows;
missing/unstable UID; renumbering; partial KSOYU; stale links; vintage SUDRF;
Moscow/non-standard magistrates; `r_juid` с уже известной карточкой, новой карточкой и
временной пустой/ошибочной выдачей.

#65 live canary ловит внешний drift; fixtures не дают сломать уже исправленное поведение
при адаптации к этому drift. Для semantic event rule обязательны positive **и negative**
fixtures: ложное юридически значимое событие опаснее пропущенного cosmetic change.

### Что брать из reference projects

- **Juriscraper** — adapter/fixture discipline и отделение scraper от persistence/app.
- **CourtSniffer** — актуальные SUDRF protocol quirks, official court code, adapter registry,
  CAPTCHA/session observations; для `msudrf` особенно ценен принцип сохранения browser/
  HTTP session после CAPTCHA. Не переносить Puppeteer/RuCaptcha/TLS bypass как default —
  #164 сначала проверяет тот же протокол чистым HTTP.
- **tochno-st/sudrfscraper** и **dataout-org/sudrfparser** — corpus/legacy oracle, не stack.
- **OlegSirik/sudrf-proxy** — `discovery → local snapshot → refresh → diff → changes` как
  product mental model.
- **alexxmirny/sudrf_parser** — свежий минимальный `fetch → snapshot → diff → changelog →
  notification`, `r_juid` и content/header-based parsing; raw field/index diff и URL-hash
  identity использовать только как антипример.
- **CourtListener** — future server-scale ingestion/workers/search reference, только для #149.

### Явно не делать

- не replatform-ить рабочий native client на Python/Node/Java;
- не делать browser automation штатным транспортом обычных `sud_delo` страниц;
- не отключать TLS verification ради проблемного суда;
- не считать CAPTCHA/error/unknown HTML за `0 results`;
- не использовать human case number или URL как identity;
- не строить feed/Calendar/server notifications через независимые diff-алгоритмы;
- не переписывать SwiftData до измеренной проблемы;
- не тащить Elasticsearch/Redis/Celery/queue infrastructure до server-scale workload;
- не ставить LLM/AI в critical path процессуального статуса, identity или срока.

## Рабочие договорённости

- Одна задача = одна ветка = один номер версии (`AGENTS.md`).
- TestFlight собирается из актуального `main`; отдельную постоянную ветку для дистрибуции
  не вести.
- Промоушен changelog — последним коммитом в ветке перед мёрджем.
- План — `Docs/roadmap.md` в репозитории; обновляется в той же ветке, что и задача.
- Ключевое слово закрытия в PR писать по-английски (`Closes #N`), иначе issue не закроется.
- Воспроизводить дефект до правки: формулировка причины в issue четырежды оказывалась
  неверной, включая одну мою собственную догадку.
- Чужие осознанные решения (комментарии «почему так») не откатывать молча — выносить на
  решение автора.
- Находки self-review: фоллаут собственной правки — чинить в том же PR; соседний дефект —
  заводить issue.
- Визуальные решения не угадывать по коду: рисовать варианты и давать выбрать.
- При каждом обновлении плана перечитывать **весь** список открытых issues, а не только
  те, что уже стоят в очереди: автор заводит новые по ходу, и они не попадают в план сами.
