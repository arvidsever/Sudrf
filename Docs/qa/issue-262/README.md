# #262 — подтверждённая база журнала событий

## Источник и границы

Проверка 4 октября 2026 года. Исходный код: `origin/main`,
`e51de294a8a8268393c8522a2886052ea6f55113`. Данные синтетические;
рабочая база, предоставленная копия и TestFlight не используются.
Новые элементы интерфейса отсутствуют. Приёмка относится к shadow-журналу,
а не к переводу ленты и уведомлений на него (#179).

## Воспроизведение до исправления

На исходном коде нативный тест через `RefreshCenter` и временное дисковое
SwiftData-хранилище воспроизводит потерю события: полный A → неполный B →
повторное открытие базы → полный B. Карточка для показа содержит B, журнал
содержит ноль событий вместо одного `judgeChanged`. Повторное обновление
историю не восстанавливает. Сборка исходного варианта успешна, проверка падает
на ожидаемом отсутствии события.

Тест: `Issue262SemanticBaselineTests/testPartialOwnCourtChangeSurvivesDiskReopenAndEmitsOnceOnCompleteRefresh`.
Локальный исходный лог: `/private/tmp/issue262-beforefix.log`; в PR не публикуются
полные системные логи. SHA-256 лога:
`c910319210fa7137d4877e977e611e1f4d38cdfb8fe0133505af359efef20a3d`.

## Согласованное поведение

- Каждый суд имеет самостоятельную обработанную базу. Полностью подтверждённый
  суд фиксирует событие сразу, даже если вся цепочка неполна; отказ карточки
  этого же суда задерживает обработку всего суда.
- Отсутствие свежего подтверждения и сохранённая ссылка не устанавливают базу.
  Подтверждённая пустая выдача не стирает уже обработанные производства;
  для ранее не встречавшегося суда она фиксирует проверенное отсутствие,
  чтобы его последующее появление стало новым событием.
- Общий признак вступления дела в силу и автоматические сроки ждут полного
  ответа цепочки; ручное изменение срока подтверждается отдельно.
- Первая достоверная база старой записи устанавливается без старых событий.
  Существующие события и occurrence ID v6 сохраняются.
- Свежие метаданные загрузки не переносятся из кэша. Базы журнала сохраняются
  атомарно с событиями и переживают перезапуск и объединение записей.

### Синтетические последовательности

| Проверка | Наблюдаемый результат |
| --- | --- |
| Полный A → неполный свой B → reopen → полный B → повтор B | В показе B; до подтверждения база A; затем ровно один judgeChanged A→B. |
| Свой B полный, вышестоящий X недоступен → его неполный Y → полный Y | A→B появляется сразу; X→Y позже; повтор не дублирует события. |
| Две карточки одного суда, неполная выдача | Обе прежние базы сохранены; после reopen полного ответа — оба изменения один раз. |
| Разные московские aliases, один портал | Полный alias обрабатывается независимо; его события не смешиваются с отказавшим судом. |
| Неизвестная общая ошибка Москвы → полный ответ | Судебные факты, вступление в силу и новый автоматический срок ждут подтверждения. |
| Объединение ожидающих баз → reopen | Сохранены базы всех судов, подборки и журнал; ожидающие изменения обнаруживаются после полного ответа. |
| Конфликт баз → reopen → подтверждение | История сохранена; спорная база устанавливается молча; следующее изменение записывается. |
| Ошибки append, encoding, save | Движение, снимок, базовая оценка и журнал откатываются вместе; следующая попытка фиксирует изменение. |
| Исправление ошибочного адреса той же карточки | Перенос только по exact native/card UID/register доказательству; прежние обработанные факты сохраняют ожидающее изменение. Одинаковый обработанный текст акта не становится новым. |
| Legacy без базы, неизвестное покрытие, повторные попытки | Исторические события не восстанавливаются; старые события и ID сохранены. |
| Ручная правка одного срока во время partial | Обновляется только этот срок в общей базе; судебные и остальные автоматические факты не продвигаются. |

Проверки в `Issue262SemanticBaselineTests` используют временное дисковое
SwiftData-хранилище, штатный RefreshCenter и MovementService с подменным
CaseProviding. `Issue262ClientPersistenceTests` дополнительно проводит
синтетический HTML через **реальный SudrfClient с подменным URLProtocol**, HTML-парсер,
MovementService, RefreshCenter и повторное открытие дискового store. Кэши и
HTTP-сессия изолированы; внешних запросов в этом тесте нет.

Необходимая свежая полнота проверяется до cache merge. Сохранённые coverage
метаданные удалены из движения на диске. Типизированный partial поисковой
выдачи, ошибка одной карточки и неопределённая принадлежность не превращаются
в успех после загрузки другой известной ссылки. Пустая выдача не удаляет
старые производства. Ручная CAPTCHA сохраняет показ и вызывает штатный
refresh, не продвигая обработанные базы самостоятельно.
