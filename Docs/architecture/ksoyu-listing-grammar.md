# Грамматика перечня дел КСОЮ (`name_op=r` без запроса)

Документ фиксирует, как получить с сайта кассационного суда ОСЮ **весь список дел
картотеки за период**, а не одно дело по номеру. Это единственная механика ГАС, которой
нет ни в `SudrfKit`, ни в навыке `sudrf-case-search`: весь существующий код ищет по
конкретному № дела, УИД или ФИО.

Знания собраны из трёх источников; у каждой строки ниже указан провенанс, потому что
надёжность у них разная.

| Источник | Что дал | Свежесть |
| --- | --- | --- |
| `sudrfscraper` (Java, опенсорс) | Грамматика перечня, ротация `srv_num`, ссылка на текст акта | ~2 года |
| `sudtudtestbot` (Node, использование разрешено автором) | Живой опыт 2026: `srv_num`, параметры кассационных производств, поведение капчи | актуальна |
| `SudrfKit` (наш) | Структурный разбор карточки и актов, справочники | актуальна |

## 1. URL перечня

```
https://<N>kas.sudrf.ru/modules.php?name=sud_delo
  &srv_num=<1..3>
  &name_op=r
  &page=<N>
  &delo_id=<DELO_ID>&case_type=0&new=<NEW>&delo_table=<TABLE>
  &<TABLE>__ENTRY_DATE1D=<дд.мм.гггг>&<TABLE>__ENTRY_DATE2D=<дд.мм.гггг>
  &Submit=%CD%E0%E9%F2%E8
```

Все прочие поля формы отправляются **пустыми** — именно пустой набор полей при заданном
диапазоне дат и даёт сплошную выдачу. `Submit=%CD%E0%E9%F2%E8` — «Найти» в cp1251,
без него выдачи нет.

### Параметры картотек КСОЮ

| Картотека | `delo_id` | `new` | `delo_table` | Префикс полей | Префикс документа |
| --- | --- | --- | --- | --- | --- |
| Гражданская кассация | `2800001` | `2800001` | `g33_case` | `G33_` | `G3_DOCUMENT__` |
| Уголовная кассация | `2450001` | `2450001` | `u33_case` | `U33_` | `U3_DOCUMENT__` |
| КАС-кассация | `43` / `2550001` — см. §6 | `0` | `p33_case` / `adm33_case` | `P33_` / `ADM33_` | — |
| КоАП (вступившие в силу) | `2550001` | `0` | `adm33_case` | `ADM33_` | — |

Префикс документа намеренно короче префикса дела (`G3_DOCUMENT__` при `G33_CASE__`) —
это особенность платформы, не опечатка.

**Внимание:** `CartotekaRegistry.cassationSOYu` (`Sources/SudrfKit/Cartoteka.swift:359-387`)
хранит короткие `delo_id` (`5` и `4`) с длинным `new`. Для карточки и поиска по номеру это
работает, но три независимых источника — `sudrfscraper`, `sudtudtestbot` и SKILL.md
(«Нормализация `delo_id`», строки 145-150) — для выдачи требуют нормализованный
`delo_id`. См. чек-лист в §7.

### Фильтры, полезные для сбора

| Параметр | Смысл |
| --- | --- |
| `<TABLE>__ENTRY_DATE1D` / `ENTRY_DATE2D` | диапазон дат поступления — основная ось нарезки корпуса |
| `<TABLE>__RESULT_DATE1D` / `RESULT_DATE2D` | диапазон дат рассмотрения |
| `<DOC>__PUBL_DATE1D` / `PUBL_DATE2D` | **диапазон дат публикации акта** — основа инкрементального добега: акт часто публикуется много позже рассмотрения |
| `<TABLE>__RESULT_DATE_I1D` / `RESULT_DATE_I2D` | дата решения первой инстанции |
| `<PREFIX>CASE__COURT_I_REGION_ID`, `<PREFIX>CASE__COURT_I` | регион и суд первой инстанции |
| `<PREFIX>CASE__CASE_NUMBER_ISS` | номер дела в первой инстанции |
| `<PREFIX>CASE__JUDGE`, `<PREFIX>CASE__RESULT` | судья, результат рассмотрения |

Даты — в формате `дд.мм.гггг`. Кириллица в любом значении кодируется в windows-1251
(`Cyrillic1251.percentEncodeQueryValue`), не в UTF-8.

## 2. Пагинация

`&page=N`, начиная с 1 (провенанс: `sudrfscraper`, `SUDRFStrategy.rotatePage`). У винтажного
интерфейса параметр называется `_page` — но у КСОЮ винтажного варианта нет
(`VNKOD_PATTERN_CASSATION` в `sudrfscraper` пуст), поэтому для кассации актуален только
`page`.

Признак конца — страница без новых строк. Сверху выдачи есть счётчик
«Всего по запросу найдено — N»; его уже умеет читать `SearchPageClassifier`, и именно он
служит контролем полноты обхода.

## 3. Ротация `srv_num`

У крупных судов **несколько экземпляров базы**, и дела распределены между ними. Подтверждено
обоими внешними источниками: `sudrfscraper` перебирает `srv_num` после исчерпания страниц
(`SUDRFStrategy.rotate`), `sudtudtestbot` перебирает `srv_num` 1..3 и кэширует рабочий
номер в своей БД.

`SudrfURLBuilder` до сих пор жёстко слал `srv_num=1` — то есть часть дел не видел ни сбор,
ни само приложение. Параметр добавлен (см. changelog ветки); клиентская ротация — отдельная
задача, её нельзя включать без живой проверки.

Порядок обхода: `page` до конца → `srv_num + 1` → снова `page`.

## 4. Строка выдачи

Таблица `<table id="tablcont">` (подтверждено кодом 2026 года). Колонки:

| # | Содержимое |
| --- | --- |
| 0 | № дела + **ссылка на карточку** (`name_op=case`, оттуда `case_id` и `case_uid`) |
| 1 | дата поступления |
| 2 | стороны / существо |
| 3 | судья |
| 4 | дата решения |
| 5 | результат |
| 6 | дата вступления в силу (не у всех судов) |
| последняя | **ссылка на текст судебного акта** |

Ссылка на текст — находка из `sudrfscraper` (`GeneralParser.scrap`, `LinkType.TEXT`),
и она меняет экономику сбора: строка уже содержит все реквизиты, поэтому при живой ссылке
**на базовый корпус хватает одного запроса на дело** вместо двух. Карточка нужна только там,
где важны движение, полный состав сторон и реквизиты нижестоящего суда.

`ResultsParser.parse` (`Sources/SudrfKit/ResultsParser.swift:17`) цепляется только за
`a[href*=name_op=case]` и ссылку на текст теряет — для приложения это неважно, для сбора
существенно.

Контейнеры текста акта по убыванию частоты: `#content`, `#tab_content_Document1`,
`#tab_content_Docs`, `.Section1`. Внутри карточки текст лежит в `cont_doc{N}` — это
надёжнее, и структурный разбор уже есть в `CaseCardParser.parseActs`
(`Sources/SudrfKit/CaseCardParser.swift:567`).

## 5. Капча на перечне

Свойства портала, добытые практикой (провенанс: `sudtudtestbot`, `docs/captcha-solver.md`
и комментарии в `server/sudrf.js`):

- **Одна капча держится на IP по несколько минут и не меняется от неверных ответов.**
  Ошибиться почти бесплатно; повторять осмысленно только на новой картинке, поэтому хэши
  проваленных картинок запоминаются, а между попытками ждут смены.
- **Решённая пара `captcha`+`captchaid` действует на весь регион**, порядка 6 часов.
  То же видно в `sudrfscraper`, где один токен в `captcha<регион>.properties` обслуживает
  два десятка судов. Для массового сбора это ключевой факт: капча решается раз на регион,
  а не на запрос.
- **Есть антибрутфорс-суды** (известен Краснодарский краевой): авто-сабмит там накапливает
  блокировку «Информация временно недоступна» на IP и портит последующий ручной ввод.
  Список таких судов ведётся явно, авто-сабмит для них выключается.
- Карточка (`name_op=case`) капчей не защищена ни на одном суде, включая КСОЮ.

Капча у КСОЮ непостоянна: у 2 КСОЮ её нет (прямой GET работает), у 3 КСОЮ есть.

## 6. Расхождения между источниками

| Вопрос | `SudrfKit` | `sudrfscraper` | `sudtudtestbot` | SKILL.md |
| --- | --- | --- | --- | --- |
| Гражданская кассация, `delo_id` | `5` | `2800001` | `2800001` | `2800001` |
| Уголовная кассация, `delo_id` | `4` | `2450001` | `2450001` | `2450001` |
| КАС-кассация | `43`, `p33_case` | `43` | **`2550001`, `adm33_case`** | `43`, `p33_case` |

По гражданской и уголовной три внешних источника согласны — для выдачи берём
нормализованный `delo_id`. По КАС-кассации `sudtudtestbot` утверждает, со ссылкой на живую
проверку дела 16-2843/2026, что она лежит в `adm33_case` вместе с КоАП и различается
номером и статьёй в строке. Это расходится с остальными и решается одним запросом.

## 7. Чек-лист живой проверки

Из песочницы Claude домен `sudrf.ru` недоступен (`403 host_not_allowed`), поэтому всё ниже
выполняется на машине с прямым доступом. Пункты 1-4 закрывают то, что известно только
из двухлетнего источника.

1. **Перечень.** URL из §1 на `2kas.sudrf.ru` (капчи нет), гражданская кассация, окно
   в неделю. Число строк совпадает со счётчиком «Всего по запросу найдено»?
2. **Пагинация.** `&page=2`, `&page=3` дают новые строки, а не повтор первой?
3. **Диапазоны дат.** `g33_case__ENTRY_DATE1D/2D` сужают выдачу ожидаемо?
   Отдельно `G3_DOCUMENT__PUBL_DATE1D/2D` — от него зависит инкрементальный добег.
4. **Ссылка на текст** в последней колонке есть? Её содержимое совпадает с текстом
   из `cont_doc{N}` карточки?
5. **`srv_num`.** Сколько экземпляров отдают данные и различаются ли выборки? Это главный
   риск незаметно неполного корпуса.
6. **`delo_id`.** Подтвердить нормализованные значения и решить вопрос по КАС-кассации (§6).
7. **Капча.** На `3kas.sudrf.ru`: сколько страниц перечня проходит на одной решённой паре.

Каждый ответ сохраняется фикстурой — по инварианту репозитория «новый вариант страницы
сопровождается парсером и фикстурным тестом» (`Docs/architecture/repo-map.md`).
